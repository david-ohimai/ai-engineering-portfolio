01 / Guided bootcamp project

DocuChat

A multi-user "chat with your documents" backend. Upload a PDF, ask a question, and get an answer drawn only from that document, with citations to the exact passages.

View repository

Problem

LLMs don't know what's in your files. Ask about your own handbook and they either refuse or invent an answer.

Solution

Fetch the relevant passages first, then have the model answer from those passages only, with each claim linked to its source.

Architecture: click a component

Express API

routes → controllers → services → repositories

    The moving dot follows one question: in through the API, a vector search in Postgres, then out to the model through the OpenAI gateway (retries and a circuit breaker).

    How a question becomes a cited answer

    1. AuthenticateJWT verified, tier permission checked, per-user rate limit applied.
    2. Embed the questionOne embedding call, cached in Redis so the same text is never paid for twice.
    3. Vector searchpgvector cosine search over chunks, scoped to this user's documents. Top-K, with a minimum score cutoff.
    4. Assemble contextPick chunks within a token budget, number them [1], [2]… and keep track of which ones were used.
    5. Build the promptSystem rules ("answer only from context, cite sources") + context + history + question.
    6. Call the modelTemperature 0.1, through a circuit breaker with retries. If nothing relevant was found, the model isn't called at all.
    7. Answer + citationsResponse returned with citations pointing to document, chunk and passage.
    8. Log cost + traceTokens, cost and latency recorded against a correlation ID for the audit log.

    What I built, week by week

    Authentication

    Registration, login, JWT access tokens with refresh-token rotation, logout, and middleware that puts the user context on every request.

    Event-driven side effects

    An EventEmitter bus so signup logging, notifications and audit entries stay out of the auth logic.

    REST design + validation

    Plural-noun resources, correct status codes, a standard response envelope, and Zod schemas on every endpoint that takes input.

    Self-documenting API

    Versioned routes under /api/v1 and Swagger docs generated from the code.

    Layered architecture

    Route → controller → service. Only controllers know about HTTP; services take plain data, so business logic never depends on Express.

    Permissions + domain model

    Tier-based permissions; documents, chunks, conversations and messages modelled as aggregates. Paginated list endpoints without N+1 queries.

    Transactions + integrity

    Multi-step writes (upload → chunk → usage log) wrapped in transactions, plus soft delete and an audit trail.

    Queues + resilient integrations

    BullMQ document worker with exponential-backoff retries and a dead-letter queue. Axios client with timeouts, a circuit breaker, and idempotent, signature-verified webhooks.

    Caching

    Redis cache-aside on permissions, document metadata and conversation lists, invalidated by events. HTTP caching with ETags and Cache-Control.

    Rate limiting

    Redis-backed sliding-window limits per user tier, stricter on auth and expensive AI routes, with X-RateLimit-* and Retry-After headers.

    Security hardening

    Input sanitisation (XSS and prompt-injection aware), Helmet with a CSP, CORS locked to the frontend origin, and secrets kept out of code and logs.

    Observability

    Structured JSON logs with redaction, Prometheus metrics, correlation IDs carried through every log line, and dependency health checks.

    Embeddings + pgvector

    Vector columns with HNSW indexes on the chunk table, an embedding service, and a Redis embedding cache.

    Ingestion pipeline

    PDF and text extraction, recursive chunking with overlap, and a worker that embeds and stores chunks with progress and per-document cost tracking.

    RAG with citations

    Scored semantic search, token-budgeted context assembly, an "answer from context only" prompt, and retrieval quality tests.

    Cost tracking + tests

    Every embedding and chat call is priced and logged per user, and exported as a Prometheus counter. 44 unit tests cover chunking, context assembly, auth, retries and sanitisation.

    Where AI is used, and where it isn't

    • Embeddings turn chunks and questions into vectors for similarity search.
    • Generation writes the answer, limited to the retrieved context.
    • Auth, permissions, chunking, caching and cost tracking are plain code. They need to be predictable.

    Challenges and what I learned

    • Slow calls don't belong in a transaction. The first version of "send message" ran the OpenAI calls inside the database transaction, holding a connection for seconds. I moved retrieval and generation out, leaving a short write-only transaction.
    • Middleware order is a security decision. The rate limiters were mounted before authentication, so every request counted as an anonymous free-tier user. They now run after auth and key on the user and their tier.
    • Caching can break polling. Cached document metadata kept showing "pending" after ingestion finished. The worker now clears the cache on every status change.

    My contribution

    Built in class alongside the instructor, Solomon Eseme (Mastering Backend). I turned four weeks of lessons into one coherent codebase: auth, queues, caching, rate limits, observability and the RAG pipeline. Along the way I fixed ten bugs I found in the lesson code and added 44 unit tests. I can explain why each layer exists and what happens when it fails.

    02 / Group project · AI Solution Challenge

    MedVerify NG

    Photograph a drug pack and learn within seconds whether it's likely genuine, suspicious or unregistered. Every scan also feeds a hotspot map that warns NAFDAC where fakes are spreading.

    View repository

    Problem

    Counterfeit and substandard medicines are common in Nigerian markets, and buyers can't spot them at the point of purchase. Scratch codes have limited coverage and can be copied.

    Why it matters

    Fake drugs cause treatment failure, drug resistance, deaths and financial loss. Verification has to happen before the drug is taken, not after a market raid.

    Who it's for

    Patients & caregivers

    Can't spot fakes by eye. Many can't read small print or English labels.

    Pharmacists & vendors

    Have no quick way to check stock bought from wholesalers.

    Community health workers

    Dispense drugs in rural areas far from any regulator.

    NAFDAC & regulators

    Rely on slow, manual raids and tip-offs.

    Genuine manufacturers

    Their brands and packaging get copied.

    How it works

    1. Photograph the packapp or WhatsApp
    2. Read label, logo & codesAIOCR + image match
    3. Match NAFDAC recordsplain DB lookup
    4. Score the riskAIweigh conflicting signals
    5. Low risk: "Likely genuine"result + confidence level
      High risk: warn, log & alertfeeds hotspot map → NAFDAC

    Results in English, Pidgin, Hausa, Yoruba and Igbo, including voice.

    Where AI is needed, and why

    ComponentWhat it doesWhy rules alone fail
    Text recognition (OCR)Reads the NAFDAC number, batch, expiry and names from blurry, curved or badly lit photosPack photos vary too much for fixed parsing rules
    Image recognitionCompares logo, colours, fonts and layout against verified genuine packsGood fakes differ in subtle details people miss
    Risk scoringCombines visual match, record match, and expired or duplicated batches into one scoreThe signals often conflict, and yes/no rules can't weigh them
    Hotspot detectionFinds clusters of suspicious scans by location and timeSpotting new patterns across thousands of scans needs pattern analysis
    Record lookupChecks registration against NAFDAC's GreenbookNo AI. It's an ordinary database search.

    Risks and mitigations

    • Wrong outputs. Show confidence levels, never claim "100% safe", and send high-risk cases to a pharmacist or NAFDAC for review.
    • Data gaps. Partner with NAFDAC and manufacturers for pack images and batch data.
    • Access. WhatsApp and USSD channels, voice results, and pharmacist-assisted scanning.
    • Privacy + abuse. Comply with the Nigeria Data Protection Act 2023, anonymise locations, and rate-limit scans so counterfeiters can't probe the system.

    How I'd build it: my engineering take

    • Async scan pipeline. Upload returns a scan ID and a queue worker runs OCR and image matching, the same pattern as DocuChat's ingestion.
    • Exact match first. The registration number goes through a plain indexed SQL lookup. Models are only called when that check is inconclusive.
    • Pack similarity in pgvector. Image embeddings of verified packs, compared by nearest neighbour.
    • Abuse controls. Per-device rate limits and an audit log on every verdict.

    A proposed design. This group submission was a concept, not built code.

    Measuring success: proposed pilot targets

    ≥ 90%detection accuracy, checked by NAFDAC lab tests
    < 10 sfrom photo upload to result
    100kmonthly active scanners by month 12
    ≥ 50%verified hotspots acted on within 30 days
    4 / 5user satisfaction rating or higher

    Proposed targets for a 12-month pilot in Lagos, Kano and Onitsha, to be agreed with NAFDAC. These are targets, not results.

    My contribution

    Group submission for Mastering Backend's Week 3 AI Solution Challenge. My part: problem research and solution design. I researched the counterfeit-medicine problem and who it affects, and designed the scan-to-verdict flow, including where AI is needed and where a plain database lookup is enough.

    05 How I engineer

    Four rules I keep coming back to.

    Each one comes from something I built, usually after seeing what goes wrong without it.

    01

    Don't let the model answer from nothing

    If retrieval finds nothing relevant, skip the LLM. KodeBuddy routes that case to a trainer. DocuChat filters out low-scoring chunks.

    02

    Enforce access where the data lives

    Permission checks go in the SQL, not just the handler. KodeBuddy's retrieval joins on enrollments, and each tool is bound to one learner when it's created.

    03

    Assume the provider will fail

    Every LLM call has a plan B: Gemini → OpenRouter, a verified model chain in the review agent, and a circuit breaker with retries in DocuChat.

    04

    Guardrails and evals before features

    Iteration, time and cost caps go in before the agent loop. Scored eval scenarios go in before I trust a prompt change.
